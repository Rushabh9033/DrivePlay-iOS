# DrivePlay — code review and the state of the build (2026-11-03)

The whole `CarTV` app was read and the findings were **fixed**, not just
reported. This is what was found, what was changed, what was verified and what
is still open.

Everything below was measured on the **physical iPhone 13** (iOS 27) or on the
**CarPlay Simulator** attached to it. The iPhone 18 Pro simulator was not used.

---

## 1. The bugs that were found and fixed

### 1.1 The player's audio session was never activated — *the car's display stayed black*

`PlaybackManager.setupAudioSession()` set the session as

```swift
try session.setCategory(.playback, mode: .moviePlayback,
                         options: [.allowBluetooth, .allowBluetoothA2DP, .allowAirPlay])
```

Every one of those options belongs to `.playAndRecord`; `.playback` accepts
**none**. The system rejected the whole call with **OSStatus -50**, so
`setActive(true)` was never reached. An inactive session never offers the
AirPlay route — and the car's display *is* an AirPlay destination, so the
picture had no way to leave the phone.

Measured on the device, `.playback` + any option → `-50`; `.playback` alone →
OK. The options are gone; the category is the one the options belong to.

### 1.2 The voice search never listened

The sheet showed *"The operation couldn't be completed. (com.apple.coreaudio.
avfaudio error 1852797029.)"*. `1852797029` is `0x6E6F7065` — *"nope"* — and the
underlying call was `PerformCommand(*ioNode, kAUStartIO)`.

**Root cause:** the recorder's `AVAudioEngine` was **born on the player's
session**. The player holds the session as `.playback`, a category with **no
input route**, so the engine's input node reported `channels=2 rate=0.0` and
refused to start (*"IsFormatSampleRateAndChannelCountValid"*).

The engine is now built **after** the session is handed to the microphone, and
the player's session comes back when the recording ends. The overlay shows
*"The microphone could not be opened."* instead of the system's number.

### 1.3 The car's display stayed black — the player had nowhere to draw

A **video-only `AVPlayerItem` never renders without a video output**: CoreMedia
logs *"video-only item is waiting for video output"*, `timeControlStatus` stays
`.waiting` and the playhead never leaves zero — while the stream itself is
perfectly fine. On the car the phone shows no player at all, so nothing owned an
`AVPlayerLayer` and the item never started.

`VideoOutputHost` now gives the player a small output of its own whenever the
phone shows no picture, and gives it up again the moment the phone's own player
comes back.

### 1.4 A failed CarPlay template call killed the app

`presentTemplate` accepts only action sheets, alerts and voice control, so
presenting `CPNowPlayingTemplate` failed — and with `completion: nil` CarPlay
throws an `NSException` (*"If the template presentation is not successful AND no
completion block is specified, an exception will be thrown"*), which aborts the
process. Every row tap took the app down.

Every template call now carries a handler that logs the failure, and the app
configures `CPNowPlayingTemplate.shared` instead of presenting one itself — the
now-playing screen is the system's to show, and it is where the **video surface**
is drawn.

### 1.5 `AVAssetWriter.finishWriting` threw when the writer never started

The encoder starts with the first frame, so a capture that delivers none leaves
the writer in `.unknown` — finishing it raises
`NSInternalInconsistencyException` and **terminates the app**. Tapping the car's
row could kill the app. Guarded on `writer.status == .writing`.

### 1.6 The broadcast never reached the car — the relay was not listening yet

The relay only started when a CarPlay row was tapped, but the user starts a
broadcast from the **Control Center**: the extension announced its stream into a
relay that was not there yet. The relay now listens from launch.

### 1.7 The car's artwork was drawn for the wrong screen

*"Images you display in any template should be sized to a display scale matching
the scale of the `carTraitCollection`, not the scale of the iOS device's main
screen."* The car's scale is read when the scene connects and every card is
drawn at it. A logo is drawn with `AVMakeRect(aspectRatio:insideRect:)` on a
rounded card — never stretched, never clipped — and the **drawn tiles are
cached** too, so a screen that is rebuilt (every favourite change) draws
nothing that is already on it.

### 1.9 A search result picked on the car played nothing

The car's search is a `CPSearchTemplate`. CarPlay hands the app the results and
takes the selection back through
`searchTemplate(_:selectedResult:completionHandler:)` — the header says the app
must call the completion handler *"when you have handled the row selection in
the search result"*, so the row's own `CPListItem.handler` is **never** called
for a search result.

The delegate answered the completion handler and stopped: the search found
channels and played none of them. Each result now carries the channel it stands
for (remembered by the item's own identity — two channels may share a name),
and picking a result plays that channel. `CarPlaySearchTests` covers it (AC69).

### 1.10 A second, unused browser

`CarBrowserView` was a whole second implementation of the browser — its own
`WKWebView`, its own tab state, its own list of preset sites — and nothing in
the app ever presented it. The car's Browser tab uses `BrowserCatalog`, so the
dead view was a **second source of truth for the same list of sites**. It is
gone; the `WKWebView` wrapper it held moved next to the browser that uses it.

### 1.11 The device-only failures in the test suite

* A test that reads the repository cannot run on a device — `#filePath` is baked
  in at build time and points at the Mac. Seven contract tests now skip
  (`RepositoryFixture.skipUnlessPresent()`).
* *"A relay that cannot listen"* proved the failure with a privileged port; iOS
  does not refuse a port below 1024. It now takes a port that is **already
  bound**, on the **loopback** interface — a listener on every interface asks a
  phone for the local-network permission and then waits for the answer.
* *"A capture without frames falls back to the demo"* cannot happen on a phone:
  ReplayKit waits for the user's consent and never ends on its own, so the
  share sat in "Starting…" for ever. The capture is a seam now
  (`ScreenShareService(capture:)`).

## 2. Milestone 1 — the car's screen

The car renders **templates only**, never views. The four tabs are a
`CPTabBarTemplate` of four `CPListTemplate`s (Home, Favorites, Cast, Browser),
and the **system** paints the bar, the selection marker and the list chrome —
so the palette can only be expressed through the artwork the app hands over and
the tab icons, which are drawn in the app's green accent.

| Tab | What it shows |
|-----|---------------|
| **Home** | the whole playlist under "All" with its real count, then every category with its own title, count and artwork; the channels as a horizontally scrollable row of cards (`CPListImageRowItem`) and a *Show all N channels* row into the whole category |
| **Favorites** | `PlaylistStore.favoriteChannels` — the phone's own list; the store's `@Published channels` drives the refresh, so a favourite toggled on the phone is on the car at once |
| **Cast** | the real state: where the picture is, whether it plays, what the share does, and the actions each one allows |
| **Browser** | the sites of the app's own `BrowserCatalog`, opened **on the phone** — CarPlay has no web view, so this is the closest compliant interaction; the screen share carries the picture to the car |

Search is `CPSearchTemplate` over the real playlist; every row that stands for
video carries a `CPPlaybackConfiguration` with `preferredPresentation: .video`
when the build is entitled (`.audio` otherwise) — the signal that makes the
system draw the picture itself.

### The phone side

`CarOutputSwitch` puts the **"▶ 📺 Play on Car Display"** pill over the video
(the whole pill is the system's route picker) and a **"Car connected"** banner
with **"Play on Phone"** and a pause button. The picture travels the AirPlay
route; the system reports the route back (`isExternalPlaybackActive` → KVO →
`PlaybackManager.isPlayingOnCar`).

## 4. The platform constraints that are still there

1. **CarPlay draws the video, not the app.** The signal is
   `CPListItem.playbackConfiguration` (`preferredPresentation: .video`, iOS
   26.4+); the entitlement `com.apple.developer.carplay-video` is Apple-granted
   and now **is** in the profile.
2. **iOS refuses to record the screen while CarPlay is connected**
   (`RPRecordingErrorCarPlay`, -5813). The car's row therefore waits for a
   **broadcast** (the WhatsApp-style share), not for a capture.
3. **ScreenCaptureKit cannot replace the broadcast on iOS**: `SCShareableContent`
   is unavailable on iOS, and the only iOS picker captures the app's own screen.
4. **The whole ReplayKit broadcast family is "no longer supported" in iOS 27**
   except the picker, which is still there and is what the app uses.
5. **A CarPlay app cannot show a web view.** The Browser tab opens the page on
   the phone and the screen share carries it to the car — the closest compliant
   interaction.
6. **`UIBackgroundModes: audio`** normally wants the
   `com.apple.developer.avfoundation.multitasking` entitlement, which the
   CarPlay entitlements files do not carry. Changing the entitlements risks the
   signing chain, so it is reported, not changed.
7. **CarPlay trims a template silently** (`maximumItemCount`,
   `maximumSectionCount`), so every category needs its own "Show all N" row —
   which is why the Home tab has one.
