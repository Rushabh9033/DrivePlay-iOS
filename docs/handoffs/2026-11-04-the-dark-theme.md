# Handoff — the app that was only as dark as the phone (2026-11-04)

## The request

> *"browser and all things are done and i want dark theme not light theme"*

The browser work was done and is **not** reopened here. The only item in this
pass is the **appearance**.

## What was actually wrong

The app had **no dark theme**. Every colour in `CarTVTheme` is a **dynamic**
system colour (`UIColor.systemBackground`, `.label`, `.secondaryLabel`, …) and
the project had **no** `preferredColorScheme` and **no** `UIUserInterfaceStyle`
anywhere — so the app simply followed the phone's system appearance. A phone
set to light showed a white DrivePlay next to a black car.

## The fix

One key, in the app's own `Info.plist`:

```yaml
UIUserInterfaceStyle: Dark
```

`project.yml` is the **source of truth** for the plist (`AGENTS.md`), so the key
goes there and `xcodegen generate` writes it into `CarTV/Resources/Info.plist`.
The plist was never hand-edited.

Why this key and not something else:

| Option | Why not |
|--------|---------|
| `preferredColorScheme` on the root view | one view only — a sheet or a second window could still come up light |
| a Settings toggle | the user asked for **dark**, not for an option; the option would be one more thing to get wrong |
| `UIUserInterfaceStyle` in the plist | **one** switch for the whole process: every tab, every sheet, every window, every scene |

The **car** is unaffected and cannot be affected: the car paints its own chrome
and the app only hands it titles, icons and artwork. (The one colour the app
*did* hand the car — a `tintColor` that painted a green frame around every
card — was removed in the sixth pass.)

## The check

`CarTV/Tests/AppearanceTests.swift` — **AC111**:

```swift
XCTAssertEqual(Bundle.main.object(forInfoDictionaryKey: "UIUserInterfaceStyle") as? String, "Dark")
XCTAssertEqual(UITraitCollection.current.userInterfaceStyle, .dark)
```

The key is read from the **running app** (`Bundle.main`), not from a copy in the
repository — so the test proves what the phone is actually running. That is the
difference between this test and the seven repository contract tests, which
skip on the device because the checkout is not on the phone.

## Gotchas learned

- **A theme made only of dynamic system colours is not a theme.** It is the
  phone's setting wearing the app's clothes. DrivePlay is dark-first, so the
  appearance has to be stated by the app, not inherited from the phone.
- **One plist key beats a root-view modifier.** `preferredColorScheme` on the
  root view leaves every sheet and every other window on the phone's setting.
  `UIUserInterfaceStyle` in the app's `Info.plist` covers the whole process.
- **The key has to be read from the running app in a test.** A test that reads
  `project.yml` proves the repository; a test that reads `Bundle.main` proves
  the phone.
- **The car cannot be told what colour to be.** The car paints its own chrome;
  the app hands it artwork. A theme change on the phone does not reach the
  car, and no code can make it.
